# 全体仮説の分解

全体仮説（hyp の根）の結論を、少ない検証で出せるように分解する。分解の良し悪しは、ノードの数ではなく「全体仮説の結論を左右する論点を、漏れも重なりもなく、検証できる形で押さえたか」で決まる。

hyp のコマンドとデータモデルは `hyp prime` の出力に従う。

## 原則

1. **軸は1階層に1つ。** 子を切る基準を1つ決めて `axis` に書く。基準の違う切り口を同じ階層に混ぜない。
2. **作る者と確かめる者を分ける。** 分解に関わっていないサブエージェントに、MECEかどうかを毎回検証させる。この検証は省略しない。
3. **影響の大きい枝だけを掘る。** 子に「親の結論への影響」を `weight` で付け、全体仮説にとっての重み（`hyp conclude` の pending に出る値）が大きい枝から掘る。会話で話題に出たことは、掘る理由にならない。
4. **反証を探す。** 支持する材料より先に、仮説が誤りになる筋を考える。
5. **人の判断も点検する。** 人が示した軸や論点も、MECEの検証と重みの評価にかける。反対の結果が出たら、丸めずに人に返す。決めるのは人である。
6. **根拠を承認しない。** AIは根拠の候補を足せるが、承認は人が行う。

## 手順

### 0. 全体仮説を点検する
分解に入る前に、全体仮説そのものを確かめる。全体仮説は、以後すべての重みを測る基準になる。

- 何が観察されれば支持、何が観察されれば棄却と言えるか。言えなければ、検証できる形への言い換えを人に提案する。
- 対立仮説を2つ以上挙げる。全体仮説が棄却されたとき、代わりに何が正しいことになるか。
- 1つの全体仮説に複数の主張が混ざっていれば（「AすればBになり、Cも不要になる」など）、それ自体を `and` の最初の分解として扱う。

### 1. 軸を選ぶ
軸の候補を3つ以上出し、次の観点で比べる。選んだ軸と、選ばなかった軸とその理由を、親の `description` に残す。

| 観点 | 問い |
|---|---|
| 単一の基準 | 1つの基準で切れているか（時間の順、主体、対象、場合分けの条件など） |
| MECEにできるか | 漏れなく重なりなく切れるか。「その他」の箱を作らずに済むか |
| 影響が偏るか | 子ごとに親への影響の差がはっきり出るか。差が出る軸ほど、掘る枝を絞れる |
| 検証できるか | 子が、それぞれ独立に検証できる形になるか |

### 2. 子と combine を決める
- 子は2〜5個にする。それ以上になるなら、軸が細かすぎるか、2つの軸が混ざっている。
- `combine` を決める。`and` は「子がすべて成り立てば親が成り立ち、1つでも崩れれば親も崩れる」ときだけ使う。必要条件を並べただけで十分条件になっていないなら、不足している子を足すか、`and` をやめる。
- 場合分けの軸なら `cases` にし、各子に `condition` を付ける。

### 3. MECEを独立に検証する
分解に関わっていないサブエージェントに、次を渡して検証させる。結果は「問題なし」か「直すべき点（修正案つき）」で返させる。

- 渡すもの：親の仮説、軸、子の一覧、`combine`、各子の `condition`
- 聞くこと
  - 子どうしに重なりはないか
  - 漏れはないか（親が成り立つ・崩れる筋で、どの子にも入らないものはないか）
  - 軸は1つの基準になっているか
  - `combine` は妥当か（`and` なら、子がすべて成り立てば本当に親が成り立つか）

直したら、もう一度検証させる。2回直しても問題が残るなら、残った問題を人に示して判断を仰ぐ。

### 4. 重みを付ける
各子に、親の結論への影響を `weight` で付け、理由を子の `description` に書く。値は兄弟の中での相対値でよい（読むときに正規化される）。

| combine | weight の意味 |
|---|---|
| `and` / `or` | その子の判定が親の結論をどれだけ動かすか。不確かで、崩れたときに親を崩しやすい子ほど重い。すでに確からしい子は軽い |
| `cases` | その場合が全体に占める割合（例：利用者の7割がスマホなら 0.7） |

### 5. 人に提示して合意する
hyp に登録する前に、次の表で人に示す。

| 子 | 重み | 理由 | condition |
|---|---|---|---|

あわせて、軸、選ばなかった軸、`combine`、MECEの検証結果を示す。人の意見と検証結果が食い違ったら、両方を並べて返す。

### 6. hyp に登録する
合意できたら登録する。

```
hyp add <親> "<子のタイトル>"            # 子ごとに。出力された ID を控える
hyp set <親> --axis "<軸>" --combine <and|or|cases> --description "<選んだ理由と選ばなかった軸>"
hyp set <子> --weight <重み> --description "<重みの理由>" [--condition "<条件>"]
hyp check
```

### 7. 次に掘る枝を選ぶ
`hyp conclude <全体仮説> --json` を実行し、`pending` の `weight`（全体仮説にとっての重み）が大きい末端から掘る。

- 掘るのは、重みの大きい順に上位の枝だけにする。全体仮説にとっての重みが 5% 未満の枝は、人が求めない限り掘らない。
- 掘らない枝は、`description` に「掘らない理由」を書き、検証方法だけを付けて止める。
- `if_supported` / `if_rejected` を見る。その末端だけで全体仮説の結論が決まる（`supported` か `rejected` になる）なら、分解するより先に検証することを人に提案する。

### 8. 末端で止める
次の3つが書けたら、その末端はそれ以上分解しない。`--method` に書く。

- 何を観察・測定するか
- どんな結果なら棄却とするか
- 誰が検証するか：AIだけで調べられる／人の持つ情報が要る／実験が要る

## よくある失敗

| 失敗 | 対策 |
|---|---|
| 会話で出た論点から順に深掘りし、全体仮説への影響が小さい枝葉ばかり掘る | 手順7。全体仮説にとっての重みで掘る枝を選ぶ |
| 軸が曖昧で、子が重なったり漏れたりする | 手順1で軸を1つ明示し、手順3で独立に検証する |
| MECEの検証を省く | 手順3は毎階層で行う。直したら再検証する |
| `and` の子が必要条件の羅列で、十分条件になっていない | 手順2・3で、子がすべて成り立てば親が成り立つかを問う |
| 進捗の割合を、仮説が正しい確率として扱う | 進捗は判定済みの割合であって確率ではない。`and` の下では、重みの小さい子1つの棄却で親が棄却される |
| 人が示した軸や論点を確定扱いにする | 原則5。検証にかけ、反対の結果は人に返す |
